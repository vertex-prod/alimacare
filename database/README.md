# AlimaCare database

This folder contains the Supabase/PostgreSQL schema for the adaptive QR intake
form. The form routes each patient through two questions — **who is filling it
out** and **why they are visiting** — then stores only the fields that apply to
that branch.

## Apply the schema

1. Open your Supabase project.
2. Go to **SQL Editor**.
3. Paste the contents of [`schema.sql`](./schema.sql) and click **Run**.

> **Warning:** `schema.sql` drops the previous AlimaCare tables and types
> before creating the new schema. Any existing patient, queue, doctor, room,
> audit, and export data will be deleted.

After running it, make sure `.env.local` contains:

```env
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
```

Restart the Next.js dev server after changing environment variables.

## Adaptive form mapping

### Router answers

| Form answer | Database column | Values |
| --- | --- | --- |
| Respondent role | `patients.respondent_role` | `self`, `guardian` |
| Visit purpose | `patients.visit_purpose` | `consultation`, `diagnostic`, `emergency` |

### Patient identity

| Form field | Database column | Rule |
| --- | --- | --- |
| Full name | `patients.full_name` | 1–120 characters |
| Unknown / unconscious toggle | `patients.identity_unknown` | emergency only |
| Date of birth | `patients.dob` | `date`; age is recalculated from it |
| Age | `patients.age` | 0–150; approximate age allowed for emergencies |
| Sex | `patients.sex` | `Male`, `Female`, `Other` |
| Civil status | `patients.civil_status` | non-emergency only |
| Home address | `patients.address` | non-emergency only |
| Patient mobile | `patients.contact_number` | required for self, optional for guardians |

### Visit, priority, and billing

| Form field | Database column | Notes |
| --- | --- | --- |
| Chief complaint / symptoms | `patients.chief_complaint` | 1–500 characters |
| Known allergies | `patients.allergies` | optional |
| Doctor's request slip | `patients.has_request_slip` | diagnostic visits only |
| Priority lane | `patients.priority_lane` | `regular`, `senior_citizen`, `pwd`, `pregnant` |
| Payment type | `patients.payment_type` | `cash`, `hmo`, `philhealth` |
| HMO provider / number | `patients.hmo_provider`, `patients.hmo_no` | required for HMO |
| PhilHealth PIN | `patients.philhealth_pin` | required for PhilHealth |
| Employer name | `patients.employer_name` | emergency / admission |
| Preferred room | `patients.room_preference` | `ward`, `semi_private`, `private`, `suite` |
| Emergency contact | `patients.emergency_contact_*` | name, relationship, number |

### Guardian / informant

| Form field | Database column | Notes |
| --- | --- | --- |
| Full name | `patients.guardian_full_name` | guardian or emergency informant |
| Relationship | `patients.guardian_relationship` | `parent`, `spouse`, `child`, `relative`, `other` |
| Mobile number | `patients.guardian_contact_number` | required for guardians |
| Valid ID type | `patients.guardian_id_type` | emergency / admission |
| Signature | `patients.signature_data` | PNG data URL from the signature pad |
| Privacy consent | `patients.consent_given` | must be `true` |

## What the database generates automatically

- **Patient ID** — `AC-YYYYMMDD-NNNN` (Asia/Manila date plus a global
  sequence), generated by `generate_patient_id()`.
- **Department** — `OPD` for consultations, `LAB` for diagnostics, and `ER` for
  emergencies. Staff can later route a ticket to another department without
  issuing a new number.
- **Ticket number** — `OPD-001`, `LAB-001`, or `ER-001`. The counter resets
  daily per prefix, and every registration gets a ticket immediately.
- **Age** — recalculated from `dob` by the trigger when a date of birth is
  supplied.
- **Status timestamps** — `called_time`, `consultation_start_time`, and
  `completed_time` are set when the status changes.
- **Status history** — every registration and status change is appended to
  `queue_events`.

## Status flow

`PENDING_RECEPTION` → `APPROVED` → `WAITING` → `CALLED` → `ONGOING` →
`COMPLETED`, plus `CANCELLED`, `NO_SHOW`, and `ARCHIVED`.

The public status endpoint also returns a live **queue position** by counting
earlier registrations in the same department that are still waiting
(`PENDING_RECEPTION`, `APPROVED`, or `WAITING`). The estimated wait uses
10 minutes per patient unless staff set a manual estimate.

## Security model

- Row Level Security is enabled on every table.
- After migration 002 (see below) anonymous visitors can only call two database
  functions: `register_patient` and `get_ticket_status`. They cannot read or
  write any table.
- Staff query with their own login; RLS policies limit each role.
- `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS and is read in exactly one file,
  `lib/supabase-privileged.ts`, used only by the AI assessment runner. Never
  import it elsewhere, never prefix it with `NEXT_PUBLIC_`, and never expose it
  to the browser.

## Quick verification

Run this after the schema:

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name in ('patients', 'queue_events', 'queue_counters')
order by table_name;
```

You should see all three tables. To inspect the newest intake:

```sql
select patient_id, full_name, visit_purpose, department, queue_number, status
from public.patients
order by created_at desc
limit 10;
```

## AI assessment, doctors and staff roles (migration 001)

`schema.sql` is destructive, so the AI assessment feature ships as an additive
migration: [`migrations/001_ai_assessment.sql`](./migrations/001_ai_assessment.sql).
It is idempotent and can be run on top of an existing `schema.sql` database.
Run it on a Supabase branch or dev project first.

It adds:

| Object | Purpose |
| --- | --- |
| `patients.symptom_duration`, `symptom_severity`, `medical_history`, `existing_conditions`, `current_medications` | Extra intake answers used by the assessment |
| `patients.clinical_department`, `triage_level`, `ai_assessment_status` | Clinical department (separate from the OPD/LAB/ER ticket prefix in `department`), provisional or validated triage level, AI run state |
| `doctors`, `doctor_availability`, `doctor_schedules` | Doctor roster, live status and Asia/Manila duty hours |
| `staff_profiles` | Role (`ADMIN`, `RECEPTION`, `DOCTOR`) for each Supabase Auth user |
| `ai_assessments`, `assessment_validations` | Versioned AI output and the staff validation decision |
| `assessment_audit_log` | Append-only record of every manual change (staff, time, original, new) |
| `doctor_workload()` | Active consultations and queued patients per doctor |

All new tables have RLS enabled and no public policies; only the server-side
service-role client reads or writes them.

### Sample doctors

The migration seeds clearly named sample doctors (`is_sample = true`). Replace
them with the hospital's real roster before any clinical use:

```sql
delete from public.doctors where is_sample;
```

### Creating the first staff user

1. In Supabase, go to **Authentication > Users** and add a user (email and password).
2. Give that user a role:

```sql
insert into public.staff_profiles (user_id, full_name, role)
values ('<auth user uuid>', 'Reception Admin', 'ADMIN');
```

For a doctor account, set `role` to `'DOCTOR'` and `doctor_id` to their row in
`public.doctors`. Doctors can then change only their own availability status.

### Environment variables

```env
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_ANON_KEY=...        # staff sign-in only
SUPABASE_SERVICE_ROLE_KEY=...            # server only
GEMINI_API_KEY=...                       # server only; never use NEXT_PUBLIC_
GEMINI_MODEL=gemini-2.5-flash            # optional; set to a model your key can use
```

If `GEMINI_API_KEY` is missing or Gemini is down, patient registration still
works. The deterministic safety rules still run, and the case is marked for
staff review.

## Least-privilege access (migration 002)

[`migrations/002_rls_least_privilege.sql`](./migrations/002_rls_least_privilege.sql)
moves the app off a database key that can read everything.

| Who | How they reach the database | What they can do |
| --- | --- | --- |
| Anonymous patient | public anon key, two functions only | Register one pending ticket; read one ticket's public status |
| Reception / Admin | their own login (RLS) | Read and update all patients, assessments, doctors |
| Doctor | their own login (RLS) | Read and update only patients assigned to them; set their own availability |
| AI assessment runner | service-role key, one isolated module | Write assessments for the patient it is processing |

Run order in the Supabase SQL editor: `schema.sql`, then
`migrations/001_ai_assessment.sql`, then `migrations/002_rls_least_privilege.sql`.

### Setup checklist

1. **Run the three SQL files** above, in order. `schema.sql` is destructive on a
   database that already holds data.
2. **Create a staff user:** Authentication > Users > Add user (email + password,
   tick *Auto Confirm User*).
3. **Give the user a role** (SQL editor):
   ```sql
   insert into public.staff_profiles (user_id, full_name, role)
   select id, 'Reception Admin', 'ADMIN' from auth.users where email = 'you@example.com';
   ```
4. **Copy the keys** from Project Settings > API into `.env.local`
   (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and the
   service-role key as `SUPABASE_SERVICE_ROLE_KEY`). Do not commit this file.
5. **Restart** `npm run dev`.
