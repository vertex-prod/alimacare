# AlimaCare database

This folder contains the Supabase/PostgreSQL schema for the adaptive QR intake
form. The form routes each patient through two questions — **who is filling it
out** and **why they are visiting** — then stores only the fields that apply to
that branch.

## Apply the schema

1. Open your Supabase project.
2. Go to **SQL Editor**.
3. Paste the contents of [`schema.sql`](./schema.sql) and click **Run**.

> **Warning:** `schema.sql` drops the previous AlimaCare tables and types
> before creating the new schema. Any existing patient, queue, doctor, room,
> audit, and export data will be deleted.

After running it, make sure `.env.local` contains:

```env
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
```

Restart the Next.js dev server after changing environment variables.

## Adaptive form mapping

### Router answers

| Form answer | Database column | Values |
| --- | --- | --- |
| Respondent role | `patients.respondent_role` | `self`, `guardian` |
| Visit purpose | `patients.visit_purpose` | `consultation`, `diagnostic`, `emergency` |

### Patient identity

| Form field | Database column | Rule |
| --- | --- | --- |
| Full name | `patients.full_name` | 1–120 characters |
| Unknown / unconscious toggle | `patients.identity_unknown` | emergency only |
| Date of birth | `patients.dob` | `date`; age is recalculated from it |
| Age | `patients.age` | 0–150; approximate age allowed for emergencies |
| Sex | `patients.sex` | `Male`, `Female`, `Other` |
| Civil status | `patients.civil_status` | non-emergency only |
| Home address | `patients.address` | non-emergency only |
| Patient mobile | `patients.contact_number` | required for self, optional for guardians |

### Visit, priority, and billing

| Form field | Database column | Notes |
| --- | --- | --- |
| Chief complaint / symptoms | `patients.chief_complaint` | 1–500 characters |
| Known allergies | `patients.allergies` | optional |
| Doctor's request slip | `patients.has_request_slip` | diagnostic visits only |
| Priority lane | `patients.priority_lane` | `regular`, `senior_citizen`, `pwd`, `pregnant` |
| Payment type | `patients.payment_type` | `cash`, `hmo`, `philhealth` |
| HMO provider / number | `patients.hmo_provider`, `patients.hmo_no` | required for HMO |
| PhilHealth PIN | `patients.philhealth_pin` | required for PhilHealth |
| Employer name | `patients.employer_name` | emergency / admission |
| Preferred room | `patients.room_preference` | `ward`, `semi_private`, `private`, `suite` |
| Emergency contact | `patients.emergency_contact_*` | name, relationship, number |

### Guardian / informant

| Form field | Database column | Notes |
| --- | --- | --- |
| Full name | `patients.guardian_full_name` | guardian or emergency informant |
| Relationship | `patients.guardian_relationship` | `parent`, `spouse`, `child`, `relative`, `other` |
| Mobile number | `patients.guardian_contact_number` | required for guardians |
| Valid ID type | `patients.guardian_id_type` | emergency / admission |
| Signature | `patients.signature_data` | PNG data URL from the signature pad |
| Privacy consent | `patients.consent_given` | must be `true` |

## What the database generates automatically

- **Patient ID** — `AC-YYYYMMDD-NNNN` (Asia/Manila date plus a global
  sequence), generated by `generate_patient_id()`.
- **Department** — `OPD` for consultations, `LAB` for diagnostics, and `ER` for
  emergencies. Staff can later route a ticket to another department without
  issuing a new number.
- **Ticket number** — `OPD-001`, `LAB-001`, or `ER-001`. The counter resets
  daily per prefix, and every registration gets a ticket immediately.
- **Age** — recalculated from `dob` by the trigger when a date of birth is
  supplied.
- **Status timestamps** — `called_time`, `consultation_start_time`, and
  `completed_time` are set when the status changes.
- **Status history** — every registration and status change is appended to
  `queue_events`.

## Status flow

`PENDING_RECEPTION` → `APPROVED` → `WAITING` → `CALLED` → `ONGOING` →
`COMPLETED`, plus `CANCELLED`, `NO_SHOW`, and `ARCHIVED`.

The public status endpoint also returns a live **queue position** by counting
earlier registrations in the same department that are still waiting
(`PENDING_RECEPTION`, `APPROVED`, or `WAITING`). The estimated wait uses
10 minutes per patient unless staff set a manual estimate.

## Security model

- Row Level Security is enabled on every table.
- No policies are granted to `anon` or `authenticated`.
- The Next.js server uses `SUPABASE_SERVICE_ROLE_KEY`, which bypasses RLS.
- Never import `lib/supabase.ts` into a Client Component or expose the service
  role key to the browser.
- The signature and full intake record are only written through server-side API
  routes. The public status page receives a reduced set of fields.

## Quick verification

Run this after the schema:

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name in ('patients', 'queue_events', 'queue_counters')
order by table_name;
```

You should see all three tables. To inspect the newest intake:

```sql
select patient_id, full_name, visit_purpose, department, queue_number, status
from public.patients
order by created_at desc
limit 10;
```
